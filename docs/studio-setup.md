# ARA Studio: Phase 1 setup

## What is implemented

Staff sign-in/out, session validation, active admin/editor membership, protected dashboard, prospect creation/editing/archiving, domain deduplication, explicit lifecycle transitions, assignment, follow-ups, search/filter/sort/pagination, staff permission controls and append-only operational history. This is part of the existing Next.js application. The public website and enquiry schema are retained.

Audit jobs, browser workers, screenshots, redesign generation, private demo sharing, outreach and client conversion are later phases. No prospect websites are fetched and no messages are sent by Phase 1.

## Choose the correct project

Use a separate ARA Supabase project in the organization selected by the founders. Do not apply these migrations to another application's database. The connected `our-table` project has not been modified. Creation of the ARA project is waiting for the requested different organization name or ID.

## Apply the migration

Inspect the target project's tables first. Apply `supabase/migrations/20261119034827_studio_foundation.sql` through the project's SQL Editor or the Supabase CLI migration workflow. This migration creates only the Studio tables/functions and does not change existing enquiry tables. Its filename was generated by `supabase migration new studio_foundation`.

Verify that `studio_users`, `studio_prospects` and `studio_activity_log` have RLS enabled. Do not expose the `ara_studio_private` schema in the Data API. Keep anonymous sign-ins and public sign-up disabled in Supabase Auth. Set Auth's sign-in rate limits for a two-person internal workspace and configure a short access-token lifetime (one hour or less). No public account registration is implemented.

## Provision the first administrator

Create a confirmed password-based user through the controlled Supabase Auth administration interface. Do not put passwords in SQL, source control or shell arguments. Retrieve that user's UUID, then execute this SQL as the database owner, replacing the placeholders with the real UUID and display name:

```sql
insert into public.studio_users (auth_user_id, display_name, role)
values ('<existing-auth-user-uuid>', '<staff-display-name>', 'admin');
```

Provision the second founder in the same way with the agreed role. Never derive authorization from user-editable Auth metadata. There are no hardcoded founder email addresses. Ordinary staff cannot insert memberships or directly update roles. The Studio settings page uses a guarded database function; editors cannot promote themselves, and the last active admin cannot be removed through it.

## Local configuration

Create the ignored `.env.local` file in the repository root. Set:

```dotenv
SUPABASE_URL=https://<ara-project-ref>.supabase.co
SUPABASE_PUBLISHABLE_KEY=<publishable-api-key>
STUDIO_ORIGIN=http://127.0.0.1:4173
```

The public enquiry integration may still need its existing `SUPABASE_SERVICE_ROLE_KEY` and provider configuration. Studio's normal database requests use the signed-in user's access token and publishable key, so RLS applies; Studio does not use the service-role key. Never expose a service-role key through a `NEXT_PUBLIC_` variable.

Run `npm ci` then `npm run dev`. Open `/studio/login`. A missing configuration displays a setup notice and grants no access. There is no local authentication bypass or production mock store. Add Body Sphere Beauty from the dashboard's first-prospect action, review the four supplied fields, then create it. Unknown contact details remain empty.

## Session behavior

The server validates every session through Supabase Auth and active membership. The database also checks the current Auth session ID and staff membership. Access tokens live only in an HTTP-only, SameSite Strict cookie scoped to `/studio`; production cookies are Secure. Session lifetime is capped at one hour. Refresh tokens are not stored; staff sign in again after expiry. Logout removes the cookie and requests provider-side local-session revocation. If the provider is unreachable, the browser cookie is still removed; provider revocation may need to be retried. Keep HTTPS enabled in hosted environments.

Updates use the record's `updated_at` as an optimistic concurrency guard. SQL triggers normalize domains, validate transitions/assignment, enforce 60 successful mutations per staff member per minute, and append activity in the same transaction. History records field names and operational state without immutable copies of notes or contact values. Archiving retains records and history; retention/deletion controls will be added during hardening, before operational production use.

## Verification

`npm test` runs existing enquiry tests, URL/input/auth permission tests and PostgreSQL integration tests using PGlite. PGlite executes the actual migration with isolated Supabase Auth schema fixtures and database roles; it does not contact a live prospect or hosted Supabase project. These tests cover RLS, creating/editing/archiving, domain collisions, lifecycle guards, append-only history, stale updates, role escalation, the final admin, anonymous access and revoked sessions. Live Supabase Auth/Data API behavior must be verified after project provisioning.

Run `npm run typecheck` and `npm run build`. Verify public routes and forms still behave as before, `/studio` redirects unauthenticated visitors, and Studio responses carry `noindex` and private/no-store headers. No Studio link is added to public navigation or sitemaps. Analytics and consent UI do not run on private routes.

After building, `npm run test:studio:e2e` starts an isolated production application on port 4184 and a temporary Auth/REST fixture provider on 4185. It exercises staff login, cookies, the dashboard, prospect creation/editing/history, duplicate and stale-write protection, CSRF and logout against the actual PostgreSQL migration. The temporary provider and database exist only in the test process and are closed afterward. These are deterministic provider fixtures, not a live Supabase integration test. A trusted loopback HTTP Supabase URL is supported for local verification; external provider URLs require HTTPS.

For the optional browser form/layout check, run `npm run test:studio:e2e -- --browser`. It uses an existing Chrome installation (Windows default path, or `CHROME_PATH`), a separate browser profile and the same fictional fixtures. It checks the real sign-in and creation forms at desktop and phone widths. Screenshots and the temporary profile remain in ignored `work/studio-browser-qa`; they are test material, not real prospect evidence.

## Deployment

Deploy the existing Next.js app to a server-capable host (for example its documented Vercel Next.js setup). Static GitHub Pages cannot run the authentication or database handlers. Set the same Supabase variables and the exact production HTTPS `STUDIO_ORIGIN` in the host, provision staff, apply/review the migration and run security advisors against the selected ARA project before enabling operational use. Keep preview and production configurations separate. No browser worker or additional paid service is required for Phase 1.
