# Website audits

Save a prospect with its public HTTP or HTTPS website. Open the prospect and select **Run website audit**. The audit action uses the saved URL, waits for the bounded inspection, saves the report and opens it. URL changes must be saved first. Previous reports remain available from the prospect and the **Audits** navigation item. The list shows the latest 50 attempts.

Reports contain observed page evidence, 16 automated checks and four manual review prompts. Checks cover title/description/headings/canonical/indexing, viewport and zoom settings, language/image alternatives/form labels, HTML response time/document size/script attributes, contact actions, HTTPS and HTTP asset references. Recommendations accompany every warning. This is a single-page baseline HTML audit. It does not execute JavaScript, visually assess design, generate screenshots, test interactions or produce Lighthouse/Core Web Vitals measurements. A client-rendered page can need manual review even when its HTML signals are missing. The number of checks passed is not a site quality score.

The server fetches the page directly without cookies, credentials, browser automation or paid AI APIs. Every hop validates the scheme/host/port, resolves public IPv4 addresses and pins the approved address on the request socket while retaining hostname-based TLS verification. Private, reserved and IPv6 destinations fail closed. The same controls apply to robots.txt redirects. Robots allow/disallow rules are checked before each page request; unavailable crawler rules fail closed, except absent robots files (404/410). Request bodies are limited to 1.5 MB for HTML and 128 kB for robots. Compressed responses are rejected if the site ignores the identity encoding request. Total network work is bounded to 22 seconds, each socket has an 8-second timeout and page redirects are capped at four. Scripts and external assets are not fetched.

The API requires current staff membership, a same-origin JSON POST and an existing non-archived prospect. It accepts no arbitrary URL in the body. Studio uses the staff access token and publishable key. The database snapshots the saved website, rate-limits requests, serializes starts per prospect and records started/completed/failed activity in the same transaction. RLS excludes non-staff. Report completion is limited to its requester; terminal reports and target fields are immutable through staff grants. There is a one-minute cooldown per prospect, an in-flight window of two minutes and a limit of 20 starts per staff member per hour.

Execution runs within the server request rather than a durable background worker. Keep the request open until the result is saved. If the app stops, the provider is unavailable or staff access expires before completion, the history may retain an unfinished attempt. After two minutes it is displayed as interrupted and a new attempt can be started. A failed attempt has no successful score. Audit completion does not automatically change the prospect lifecycle; staff can review findings before updating the stage.

## Verification

`npm test` passes 57 checks, including audit target/redirect/DNS/robots/report tests and actual PostgreSQL migration tests for snapshots, report persistence, RLS, immutable history, duplicate starts and failure states. `npm run lint` and the production build pass. `npm run test:studio:e2e` verifies the running production application against isolated Auth/REST/PostgreSQL fixtures, including saved audit detail/list/prospect views, successful and failed audit service execution, repeat-run protection, CSRF and strict API input. Website responses in that test are injected into the server service; no authentication bypass or fixture fetcher is mounted in the application.

The Supabase audit migration was applied and verified: RLS is enabled, three audit policies exist and anonymous table reads are not granted. A live website request could not be verified from the restricted execution environment. The optional browser fixture harness also failed during browser startup; its results are not included in the passing end-to-end claim. The updated local sign-in page was checked separately in the in-app browser.

Existing security notices remain: the framework build raised a Next.js upgrade recommendation, and Supabase reports [leaked-password protection disabled](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). The private write-limit table deliberately has no public RLS policies; only its guarded private functions access it.
